# FocusBridge 실제 사이트 수집 데이터 (2026-11-04)

## 이 모음집은 무엇인가

크롬 확장 프로그램 **FocusBridge**(① 검사 대상 수집 + ② 이름 누락 탐지)를 실제 사이트 10곳의 첫 화면에서 돌리고, **"스크린리더가 기능 이름을 읽어 줄 수 없다"고 판정된 버튼·링크**를 사이트별로 모은 것입니다.

- **용도:** 기능 사전(단어매칭목록) 작업의 B단계(판별 패턴 나누기)와 C단계(가중치·확정 기준 검증)에 쓸 원재료입니다.
- **형태:** 매칭 코드가 실제로 받게 될 입력(`report`)과 똑같은 형태입니다. 여기에 사람이 확인할 때 쓰는 `html` 하나만 덧붙였습니다.
- **원본:** 수집한 내용을 한 파일(txt)에 이어 붙였던 것을 사이트별 파일로 나눴습니다. 내용은 고치지 않았습니다.

---

## 무엇을 체크해서 가져왔나

프로그램이 페이지의 요소를 아래 순서로 걸러서, 마지막까지 남은 것만 이 데이터에 들어 있습니다.

### 1. 검사 대상 고르기 (`collector.js`)

| 기준 | 내용 |
|---|---|
| 역할 | 계산된 역할이 `button`, `link`, `tab`, `menuitem`, `checkbox`, `switch`, `option` 중 하나인 요소만. href 없는 `<a>`는 링크가 아니라서 빠집니다. |
| 숨김 요소 | `display:none`, `hidden`, `aria-hidden="true"`, `inert` 영역 안의 요소는 스크린리더도 읽지 않으므로 뺍니다. |
| 화면 밖 요소 | 눈에 안 보여도 Tab으로 가면 읽히므로 **포함**합니다. 예: 아직 안 넘긴 배너 슬라이드 |
| Shadow DOM | 열린(open) Shadow DOM 안쪽은 포함, 닫힌(closed) 쪽은 접근할 수 없어서 미포함입니다. |
| iframe | 이번 수집 방식은 페이지 본문만 모으므로, 페이지 안에 끼워진 광고·위젯(iframe) 안쪽은 들어 있지 않습니다. |

### 2. 이름 계산 (`detector.js`)

스크린리더가 읽을 이름(accessible name)을 W3C 규칙대로 계산합니다(라이브러리 `dom-accessibility-api`). 계산 순서는 `aria-labelledby` → `aria-label` → 버튼 안 글자·이미지 `alt` → `title`입니다.

### 3. 이 데이터에 넣을지 판정

| 판정 (`status`) | 기준 |
|---|---|
| `empty` | 계산된 이름이 비어 있음 → 스크린리더는 "버튼", "링크"라고만 읽음 |
| `meaningless` | 이름은 있지만 기능을 알 수 없음: 정해진 의미 없는 단어(`button`, `아이콘`, `x` 등), 기호나 숫자만 있는 이름, 파일명이나 주소 형태의 이름 |
| `ok` | 기능을 알 수 있는 이름 → **이 데이터에는 들어 있지 않습니다** |

### 4. 시점

각 페이지를 맨 아래까지 스크롤한 뒤의 **마지막 검사 결과**입니다. 누적이 아니라 그 순간의 상태입니다.

## 파일 구조

모든 파일은 같은 구조의 JSON입니다.

```
{
  "url":         수집한 페이지 주소
  "collectedAt": 수집 시각 (세계 표준시, 한국 시간은 +9시간)
  "items": [     이름이 누락된 요소 목록 (없으면 빈 목록 [])
    { 요소 하나 }, ...
  ]
}
```

### 요소 하나의 필드

| 필드 | 뜻 |
|---|---|
| `no` | 페이지 안에서의 순번 (1부터) |
| `status` | 판정: `empty` 또는 `meaningless` |
| `role` | 계산된 역할: `button`, `link` 등 |
| `currentName` | 지금 스크린리더가 읽는 이름 (`empty`면 빈 글자) |
| `selector` | 요소를 다시 찾기 위한 간이 경로 (디버깅용) |
| `context.tagName` | 태그 이름: `a`, `button`, `div` 등 |
| `context.id` | 요소의 id |
| `context.className` | 요소의 class |
| `context.href` | 링크 주소 |
| `context.iconClass` | 요소 안 **첫 번째** 아이콘(svg, img, i, class에 icon이 든 요소)의 class |
| `context.iconSrc` | 같은 아이콘의 그림 주소 |
| `context.parentClass` | 바로 위 부모 요소의 class |
| `context.parentText` | 부모 요소 안의 보이는 글자 전체, 앞 100자 (요소 자신의 글자도 섞여 있음) |
| `context.prevSiblingText` | 바로 앞 형제 요소의 글자, 앞 50자 (태그 없이 글자만 있는 형제는 안 잡힘) |
| `context.nextSiblingText` | 바로 뒤 형제 요소의 글자, 앞 50자 |
| `context.rect` | 화면 위치와 크기 (x, y, 너비 w, 높이 h, 픽셀 단위) |
| `html` | 요소의 HTML 원문 앞 300자. **판별에는 쓰지 않고**, 사람이 실제 기능(정답)을 판단할 때만 봅니다. |

값이 없는 필드는 `null` 또는 빈 글자(`""`)입니다.

## 알아 둘 점

- **항목이 0개인 사이트가 3곳 있습니다** (11번가, 유튜브, 네이버). 정말 누락이 없는 것인지, 검사가 덜 된 것인지는 이 데이터만으로는 구분할 수 없습니다. 콘솔의 `[FocusBridge] 대상 N개 / 이름 누락 0개` 줄에서 **대상 수가 충분히 크면**(수십~수백 개) 실제로 누락이 없는 것입니다.
- **방문할 때마다 결과가 달라질 수 있습니다.** 배너, 광고, 추천 상품, 뉴스 기사는 계속 바뀌므로, 같은 페이지를 다시 모으면 항목 수와 내용이 다를 수 있습니다.
- **주소의 광고 추적 값:** 11번가, 무신사, 트립닷컴 주소에는 광고를 클릭해서 들어온 기록 값(`gclid`, `NaPm` 등)이 붙어 있습니다. 이름이나 계정 정보는 아니지만, 팀 밖에 공유할 때는 `?` 뒤를 지워도 됩니다.
- **정답(실제 기능)은 `labels.json`에 따로 있습니다** (아래). 수집 파일 자체는 고치지 않았습니다.

## 정답 파일 `labels.json` (B단계에서 추가)

98개 항목마다 `html`과 문맥 정보를 보고 실제 기능을 사람이 정한 것입니다. C·D단계에서 매칭 결과를 채점하는 기준으로 씁니다.

| 필드 | 뜻 |
|---|---|
| `site`, `no` | 어느 파일의 몇 번 항목인지 (`coupang` + `1` → `coupang-main.json`의 1번) |
| `kind` | `function`(기능형: 메뉴·검색 같은 사이트 공통 기능) / `content`(콘텐츠형: 상품·기사·배너처럼 이름이 내용 자체인 것) |
| `pattern` | 판별 패턴 코드 (아래 표) |
| `answer` | 붙여야 할 이름. 콘텐츠형이거나 기능을 알 수 없으면 `null` |
| `note` | 정답을 정한 근거, 함정 |
| `expected` | **우리 모듈이 내야 하는 결과** (C단계에서 추가). 이름 목록이면 그중 하나로 확정해야 정답이고, `"AI"`면 AI로 넘겨야 정답(사이트 전용 기능이거나 단서 없음)입니다. `"content"`면 콘텐츠형으로 가려내거나 AI로 넘겨야 하며, 이름을 붙이면 오답입니다. |

`answer`와 `expected`가 다를 수 있습니다. 예를 들어 나무위키 "최근 변경"은 정답 이름(`answer`)은 알지만, 사전에는 사이트 공통 기능만 넣기로 해서 `expected`는 `"AI"`입니다.
